### 关键行为

- **接收统计**：累计帧数、距上次收到秒数、2 秒滑窗频率、原始 int16、来源 CAN ID、
  字节序（BE/LE）、量纲（×1/×10/×100）、`data[6..7]` 的 2 秒取值范围、连续同值帧数
- **画面四态**：
  - 绿 `[RX OK]` —— 电控正在稳定发，数值可信
  - 橙 `[UNSTABLE]` —— 能解出数但值在跳，**说明这两字节不是弹速**
  - 橙 `[RX LOST x.xs]` —— 以前收到过，现在断了
  - 红 `[NOT RECEIVED]` —— 从没收到，显示的 11 m/s 是构造函数默认值
- **收不到时把 0x106 整帧摊开**：`bytes: XX XX ...` + `BE 0x????=??` + `LE 0x????=??`
- **0x106 Hz 与 speed Hz 并排**：两者相等=每帧都带弹速；0x106 高而 speed 低=那两字节不是弹速
- **安全阀**：`kStableFramesNeeded = 5`，连续 5 帧解出的弹速基本一致才写 `bullet_speed`，
  乱跳的值只记账不参与瞄准解算

## 3. 已查实的关键结论

### 3.1 弹速：`data[6..7]` 里装的不是弹速

日志实测（`logs/2026-09-24_17-22-10.log`）：

```
raw=28  -> 28.00 m/s (little-endian, x1)
raw=9   ->  9.00 m/s (big-endian,    x1)
raw=25  -> 25.00 m/s (little-endian, x1)
raw=256 -> 25.60 m/s (little-endian, x10)
```

同一个物理量一会儿 28、一会儿 9、一会儿 25、一会儿 25.6，**字节序和量纲都在跳**
——典型的"变化的值偶尔撞进判定窗口"，不是稳定的弹速。

**待电控确认**：弹速到底放在哪个字节、用什么量纲、大端还是小端。

### 3.2 云台停转：不是没电，是视觉主动发 `control=0`

`command_builder.cpp:18-20`：

```cpp
io::Command disabled_command() { return {false, false, 0.0, 0.0}; }  // control=0, yaw/pitch=0
```

日志里每一帧 `control 0` 都同时是 `yaw +0.00 / pitch +0.00`，且 `[TX->EC]` 每秒一条从未中断
→ **进程活着，是"没有目标"的正常表现**。电控收到 `control=0` 就不动云台。

### 3.3 丢目标的三个机制

**① EKF 几何状态发散（主因）**

`target.cpp:241-250`：

```cpp
r_ok = ekf_.x[8] > 0.05 && ekf_.x[8] < 0.5;                 // 半径 r
l_ok = ekf_.x[8] + ekf_.x[9] > 0.05 && ekf_.x[8]+ekf_.x[9] < 0.5;  // r + 长短轴差 l
```

日志里估出的值全是废的：
- `l` 为负（物理上应 ≥0）：`-4.225`、`-2.567`、`-1.454`、`-0.293`、`-0.216`
- `r` 塌到阈值以下：`0.021`、`0.028`、`0.031`、`0.038`、`0.048`，一次**恰好 `0.050`**（卡边界）

而 `set_target()` 给普通装甲板初始化 `Target(armor, t, 0.2, 4, ...)`，**r 本该收敛到 0.2 附近**。

发散后 `tracker.cpp:76-80` 置 `state_="lost"` 并 `return {}` → 空目标 → `control 0`。

出现次数：1 / 11 / 4 / 2 / 8 次（最近 5 次运行）。

**② 相机掉帧**

`tracker.cpp:38-41`：`dt > 0.1s` 直接强制 `state_ = "lost"`。
17:20 那次实测 `Large dt: 0.270s / 0.156s / 0.130s`（0.27s ≈ 瞬时掉到 3.7 FPS）。

**③ 装甲板 name/type 与跟踪目标不一致**

`tracker.cpp:273`：`if (armor.name != target_.name || armor.type != target_.armor_type) continue;`

分类器把兵种名认翻 → `found_count == 0` → 返回 false → 累计 `max_temp_lost_count: 15` 帧后置 lost。
**15 帧在 60FPS 下只有 0.25 秒**，偏紧。

### 3.4 其他

- `Bad Converge` 所有日志均为 0 次，不是原因
- `[DamiaoCAN][ERR]` 总线错误：17:16 有 107 次、17:18 有 20 次，**17:20/17:22 为 0 次**
  → 最新几次不是 CAN 问题（但该错误本身值得单独查，`damiao_can.cpp:409-441` 是设备错误回调）
- **我加的 ×1 量纲（8~30）放大了伤害**：28/9/25 这些垃圾值以前会被 ×10/×100 规则拒掉，
  改后被采纳成弹速 → 弹道 pitch 摆动好几度 → 瞄偏 → 目标出视野 → 丢检测。
  最新版已加"连续 5 帧一致"安全阀，但**尚未跑过验证**，且容差 ±1.0 对"每帧 +1 的计数器"仍会失效。

### 3.5 两个诊断缺陷（未修）

1. `debug_overlay.cpp` 的 `draw_text_panel()` 画 tracker 状态 / armor 数量 / 估计器状态，
   **从来没被调用**（死代码）。`show_debug_overlay()` 只调 `draw_detection_boxes` 和
   `draw_target_debug` → **画面上看不到 tracker 状态**，而这正是区分机制①/③最需要的信息。
2. `main.cpp:129-130`：`armors_before_tracker` 和 `armors_after_tracker` 被赋成**同一个值**
   （都在 `tracker.track()` 之后取），"跟踪前后对比"是废的。
