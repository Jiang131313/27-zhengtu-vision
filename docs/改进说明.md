## 1. 姿态来源：电控电机编码器 → 四元数

### 现象

哨兵装机时 C 板 BMI088 IMU 不可用（排线/供电问题），而 `src/sentry/main.cpp` 的姿态分支在 `imu` 为空时直接退化成 `Eigen::Quaterniond::Identity()`，等于**云台转了多少视觉完全不知道**——PnP 解出来的世界系坐标是假的，自瞄不可能准。

同时项目里 `imu_enabled: true` 但 IMU 没插时会直接崩（空指针），启动都过不去。

### 根因

姿态只有两条来源：IMU 四元数，或恒等四元数。没有第三条路。

### 改法

既然电控自己就在闭环控制云台，它一定知道 yaw / pitch 电机的绝对角度。让它通过 CAN 回传编码值，视觉侧换算成四元数即可。

新增 `io/cboard_motor_pose_buffer.{hpp,cpp}`：

```cpp
// 由 CBoard 回调在收到 motor_angle_canid 帧时调用
void on_motor_angle(const can_frame & frame, std::chrono::steady_clock::time_point timestamp);
Eigen::Quaterniond imu_at(std::chrono::steady_clock::time_point timestamp) const;
```

`io/cboard.cpp` 的 `callback` 按 canid 分流，**复用同一个 CAN 后端**，不新开设备、不与指令下发争用总线：

```cpp
if (frame.can_id == motor_angle_canid_) {
  motor_pose_buffer_->on_motor_angle(frame, timestamp);
  return;
}
```

`src/sentry/main.cpp` 接入：

```cpp
io::CBoard cboard(config_path);
io::CBoardMotorPoseBuffer motor_pose;
cboard.set_motor_pose_buffer(&motor_pose);
...
if (cboard.has_motor_pose()) {
  q = motor_pose.imu_at(t + imu_time_offset);
} else if (imu) {
  q = imu->imu_at(t + imu_time_offset);
} else {
  q = Eigen::Quaterniond::Identity();
}
solver.set_R_gimbal2world(q);
```

编码值 → 角度全部配置化：

```cpp
yaw_rad   = motor_yaw_direction   * (yaw_enc   - motor_yaw_zero)   * motor_yaw_scale;
pitch_rad = motor_pitch_direction * (pitch_enc - motor_pitch_zero) * motor_pitch_scale;
```

四元数（对齐 `io/dm_imu` 的构法，**无 roll**）：

```cpp
Eigen::Quaterniond q = Eigen::AngleAxisd(yaw_rad, Eigen::Vector3d::UnitZ())
                     * Eigen::AngleAxisd(pitch_rad, Eigen::Vector3d::UnitY());
q.normalize();
```

### 实测标定的参数

| 参数 | 值 | 怎么来的 |
| --- | --- | --- |
| `motor_angle_canid` | `0x106` | 与电控约定 |
| `motor_yaw_scale` | `0.00076699` | 8192 线编码器：`2π/8192`，即 0.0439°/count |
| `motor_pitch_scale` | `0.01745329` | 电控给整度数：`π/180` |
| `motor_pitch_direction` | `-1` | 手眼标定实测，电控 pitch 正方向与云台系 Ry 相反 |
| `motor_yaw_direction` | `1` | 实测 |
| `motor_yaw_zero` / `motor_pitch_zero` | 自动 | 启动第 50 帧取零点 |

零点为什么取第 50 帧：开机头几帧编码值可能还没稳定，取到异常帧会把零点标歪。**这个坑踩过**——一次异常帧让 yaw 零点偏了约 1100°，云台上电就失控；后来补了 `motor_yaw_zero` 的 `[0, 8192)` 范围检查，超范围就丢弃这一帧。

### 效果 / 验证状态

`实机验证`。1 Hz 日志 `## rx yaw: +0.00deg pitch: +24.00deg | enc 6290 / -24 | 199.3Hz` 证明链路通、更新率约 199 Hz。

### 遗留限制（没做完的部分）

1. **无 roll**。两轴编码器还原不出滚转，底盘大机动时世界系会偏。
2. **pitch 被量化到 1°**，姿态精度上限约 ±0.5°，这是电控侧协议决定的，视觉侧无法补救。
3. **时间戳取 CAN 帧到达时刻**，不是电控产生时刻，存在总线延迟。
4. **缓存空时静默返回单位四元数**（`io/cboard_motor_pose_buffer.cpp`），CAN 断了不崩但会瞄偏，应该改成告警。

后续方向见 `docs/双Yaw轴姿态融合方案.md`（把 C 板 IMU 接回来，与两轴编码器做融合补 roll）。

## 2. CAN 下发层重构

### 现象

云台响应慢、抖，而且**方向经常反**——有时候瞄准目标是往反方向跑，最后限位。

### 根因（四个叠加）

1. **发送频率被图像帧率绑架**：`CBoard::send()` 在视觉主循环里调用，实际下发频率跟着检测耗时走（80~100 Hz 且抖动）。
2. **下发的是绝对角，电控要的是增量角**。电控 `GimbalAimReceive_Task` 里的字段语义是 `d_yaw` / `d_pitch`（增量），我发绝对角，等于让它每帧累加，云台自然朝单方向跑飞。
3. **符号没对齐**：电控"抬头为正"，云台系 Ry 是"抬头为负"，pitch 一路往上抬（闭环正反馈）。
4. **`control = 0` 时发 0 角**，被电控理解成"回零点"，目标一丢失云台就被猛甩回中。

### 改法

- **发送解耦到独立线程**，固定频率发最新一帧指令：`configs/demo.yaml` 的 `can_send_hz: 200.0`。视觉算得慢不影响下发节奏，云台看到的是一条平滑的指令流。
- 改为下发**增量角**：`d = 目标角 − 当前角`，与电控语义一致。
- `control = 0` 时发 **0 增量**（"别动"），不再发 0 角（"回零"）。
- 增量限幅：`send_yaw_clamp` / `send_pitch_clamp`，pitch 取 `+40 / −20` 度。目标跳变时云台不会被一帧指令甩到底。
- 方向 / 增益 / 偏置 / 缩放全做成配置，现场调参不重编译：`send_yaw_sign`、`send_pitch_sign`、`send_gain`、`send_pitch_bias`、`send_scale`。
- 发送端**抵消电控的 `+2°` 硬编码**：电控每帧无条件给 pitch 加 2°，视觉侧减掉，否则相当于 300°/s 的持续上抬。

### 效果 / 验证状态

`实机验证`。云台能稳定跟随、不再单向跑飞。

### 附带修掉的两个坑

- `can_interface` 原本是**另一台机器**（Jetson）的达妙序列号，在 NUC 上根本不匹配，改成 NUC 上实测的 `damiao:sn:14AA...`。
- `bullet_speed_canid` 原本是 `0x101`，但那一路被电控遥测帧占用，视觉每帧都收 `Invalid feedback` 刷屏，改成 `0x7FF` 让这一路彻底不生效。

## 3. 相机标定与手眼标定

### 内参

原来的 `configs/demo.yaml` 内参是旧镜头/旧标定板的，重新标定后 `cy` 差了约 **60 px**。PnP 和手眼标定都必须用新内参，否则距离系统性偏大。

### 手眼标定工具链（移植 + 优化）

从 Jetson 版移植 `handeye_calib`，原来直接跑全图检测，主线程被占满导致窗口无响应。改法：

1. **检测放独立线程**，UI 线程只管画。
2. **半分辨率优先** + 失败回退全分辨率 + 自动缓存"上次成功的格数"，帧率与稳定性都上来了。
3. 检测按 `1.0 → 0.7 → 0.4` 优先级降级——角点精度不够会让解出来的姿态乱跳，宁可降分辨率多拿到几帧好的。
4. 加 `d` 键导出当前帧、前 3 帧自动留存，方便离线诊断"为什么整块板识别不到"。
5. 每帧原始位姿落盘到 `/tmp/handeye_poses.txt`，供离线穷举运动学模型。

### 结果

`t_camera2gimbal` 定稿 **21 cm**（两组独立数据互印证），并与机械 CAD 实测值（226.96, 0, 137.7 mm）在 x/y 上吻合（差约 15 mm），z 方向以 CAD 为准。

pitch 符号当场由实测确认相反（一致性误差从 `9000 mm` 降到 `8.75 mm` 才敢下结论）。

### 枪口外参（`t_muzzle2gimbal`）

原来的值是 CAD 导出、绕**云台轴交点**算的，而 `t_camera2gimbal` 是相对**IMU 原点**——两个原点不一致，直接用会导致一个**与距离无关的固定偏置**。按实测（相机前 150 mm、枪口同高、上方 45 mm）重新换算后，方位偏差从"左约 7.6 cm、上约 6.8 cm"归零。

## 4. EKF 卡方门限数量级错误

### 现象

目标跟不稳、一顿一顿，日志里 `Bad Converge` 频繁出现，目标每几帧被丢弃一次又重建。

### 根因

`tools/extended_kalman_filter.cpp`：

```cpp
constexpr double nis_threshold = 0.711;   // 自由度 1 的 95% 分位
constexpr double nees_threshold = 0.711;
```

`0.711` 是 **χ²(1)** 的 95% 分位。但一次更新用 4 维测量（x/y/z 距离 + 角度），自由度是 **4**，对应 95% 分位是 **9.488**。用 0.711 等于只放行约 5% 的测量——绝大多数正常测量都被判成离群点丢弃。

### 改法

```cpp
constexpr double nis_threshold = 9.488;   // chi2(4) @ 95%
constexpr double nees_threshold = 9.488;
```

### 效果 / 验证状态

`实机验证`。修正后 `Bad Converge` 从高频降到 0，跟踪连续性明显改善。

### 教训

卡方门限必须跟着**测量维度**走。这个值是从别处抄来的，维度一改就静默失效——它不报错，只是"跟踪不灵敏"，很难联想到是统计门限。

## 5. 瞄点下发链路重写（`src/sentry/command_builder.cpp`）

### 现象

云台能跟上目标，但**打不中**。距离越远、目标横向速度越快，偏得越多。

### 根因

`tasks/auto_aim/aimer.cpp` 里做了一整套弹道解算：时间戳对齐补偿管线延迟、按旋转速度选延迟时间、10 次迭代求飞行时间与下坠角、加 `yaw_offset` / `pitch_offset`……**算完之后全部被丢弃**。

原来的 `command_builder` 只用当前帧的检测位置算角度：

```cpp
// 原来：纯当前帧检测角，无提前量、无下坠、无偏移
const Eigen::Vector3d dir_world  = armor.xyz_in_world - muzzle_world;
const Eigen::Vector3d dir_barrel = solver.R_gimbal2world().transpose() * dir_world;
return tools::xyz2ypd(dir_barrel).head<2>();
```

11 m/s 弹速、5 m 距离，下坠补偿约 **11.9°（≈50 cm 弹道落差）**，等于完全不打提前量和下坠。而且 `yaw_offset: -1` / `pitch_offset: -1.4` 这两个配置成了死配置——读了、加了，然后被覆盖。

第二个问题更致命：原实现要求**本帧必须匹配到装甲板**，否则下发 `{control=false, shoot=false, 0, 0}`。跟踪处于 `temp_lost` 缓冲期时云台直接冻结，目标随即离开视野——本该靠 45 帧缓冲救回来的目标必然进入 `lost`。

### 改法

改成"把 Aimer 的世界系瞄准方向转到枪管系再下发"：

```cpp
// Aimer 输出的是世界系下的瞄准方向（含提前量 + 下坠 + 两个 offset）
const Eigen::Vector3d dir_world  = tools::ypd2xyz({aimer_command.yaw, aimer_command.pitch, 1.0});
const Eigen::Vector3d dir_barrel = solver.R_gimbal2world().transpose() * dir_world;
const auto angles = tools::xyz2ypd(dir_barrel).head<2>();
command.control = true;
command.yaw   = angles->x() * kRad2Deg;
command.pitch = angles->y() * kRad2Deg;
```

关键点：

- 用 `ypd2xyz` / `xyz2ypd` 这一对**精确互逆**函数做转换（`pitch = atan2(z, sqrt(x²+y²))`，抬头为正），所以转换本身不引入误差，下发给电控的角度约定也完全没变。
- 顺便纠正了一处**注释错误**：`aimer.cpp` 里写着"世界坐标系下 pitch 向上为负"，实际 `tools/math_tools.cpp` 的 `xyz2ypd` 定义是**抬头为正**，`tools/trajectory.hpp` 的注释也是抬头为正。
- **去掉"本帧必须匹配到装甲板"的硬门槛**：`temp_lost` 期间继续按 EKF 预测方向控制云台，不再冻结。

### 效果 / 验证状态

`编译通过`（未做充分实弹验证）。改动可逆，回滚脚本与原文件 sha256 都在备份里。

## 6. 火控：三条件开火门（`tasks/auto_aim/shooter.cpp`）

### 现象

开火频率过高，散布大，弹药浪费；装甲板切换瞬间也会开火。

### 根因

原实现里非小陀螺情况直接：

```cpp
// 非小陀螺时不再额外做火控限制：只要前面已经判定 control=1 且存在目标，就直接开火。
fire_ready = true;
```

只要"有目标 + control 成立"就每帧开火。指令还在追、枪管还没到位、瞄点刚跳变，全都不管。

### 改法

换成同济上游的三条件门：

```cpp
const bool command_ok = std::abs(last_command_.yaw - command.yaw) < tolerance * 2;
const bool gimbal_ok  = !use_gimbal_feedback_ || (std::abs(command.yaw) < tolerance);
fire_ready = command_ok && gimbal_ok && aimer.debug_aim_point.valid;
```

| 条件 | 拦住什么 |
| --- | --- |
| 指令不突变 | 装甲板切换瞬间的假机会 |
| 云台已跟上上一次指令 | 枪管还在路上就开火 |
| 瞄点有效 | 弹道无解 / 预测不可信 |

容差按距离分档（`judge_distance` 以内用 `first_tolerance`，以外用 `second_tolerance`），因为远处角度容差对应的线偏差更大。

⚠️ 一处**必须注意的适配**：本工程 `command.yaw` 在下发链路里已经是**枪管系相对角的度**，而上游是**世界系绝对弧度**。所以这里不能用上游的 `yaw / 57.3`，`first_tolerance` / `second_tolerance` 直接按度用。

### 效果 / 验证状态

`编译通过`（未做充分实弹验证）。

## 7. 灰板（被打灭的装甲板）跟踪

### 现象

打中一块装甲板之后，目标立刻消失，自瞄重新进入搜索状态。

### 根因

装甲板被击中后熄灭变灰，检测网络把它归到 `Color::extinguish`。代码里有两处按颜色硬过滤：

```cpp
// tasks/auto_aim/tracker.cpp
armors.remove_if([&](const auto_aim::Armor & a) { return a.color != enemy_color_; });

// src/sentry/target_filter.cpp
return armor.color == enemy_color && armor.name == priority_target;
```

灰板在两处都被丢掉，EKF 拿不到测量，只能靠 `temp_lost` 缓冲硬撑，撑完就 `lost`。

### 改法

`tasks/auto_aim/tracker.cpp` 放行灰板：

```cpp
const bool keep_extinguish = (state_ != "lost");
armors.remove_if([&](const auto_aim::Armor & a) {
  if (a.color == enemy_color_) return false;
  return !(keep_extinguish && a.color == Color::extinguish);
});
```

两个设计选择：

- **只在非 `lost` 状态放行**。`lost` 时如果放行灰板，可能拿一块分不清敌我的灰板重新起锁，比丢锁更糟。
- **`target_filter.cpp` 故意没动**。那层是"优先级目标筛选"（比如优先打哨兵），语义上要求明确敌我，不适合放行灰板。

为什么放行就生效：`Target::update_target` 的匹配条件是 `armor.name == target_.name && armor.type == target_.armor_type`——**只比名字和大小，不看颜色**。EKF 里已经建好模的轨迹能直接续上灰板测量。

### 效果 / 验证状态

`编译通过`（未做实机验证）。

## 8. 调试可视化

单相机、无操作手的哨兵，最难的是"看不见它在想什么"。补了一套：

| 手段 | 解决什么问题 |
| --- | --- |
| 窗口只显示**真正下发**的增量角 + CAN 原始 int16 字节 | 原来显示的是绝对目标角 + 现算的假 raw，排查方向完全是错的 |
| 1 Hz `[TX->EC]` / `[RX]` / 差值 / 瞄准误差 并排打印 | 一眼看出是"算错了"还是"发错了"还是"电控没跟" |
| 1 Hz 打印 `control` 被关掉的**5 种原因** | 直接定位"一顿一顿"是哪个环节把指令关了 |
| 1 Hz 打印 EKF 的 NIS 失败率 | 确认目标被反复丢弃是不是卡方门限导致（就是靠它发现的第 4 条） |
| 打印视觉帧率 | 判断性能瓶颈 |
| 角度只显示 1 位小数 | 真实分辨率就是 0.1°，多位小数是假精度，反而误导 |

另外新增 `display` 独立配置 + `configs/` 下多套配置文件，把"日常跑"和"开画面调试"分开；`can_disabled: true` 时可以完全不接电控跑视觉（用单位四元数），只验证识别与跟踪。

## 9. 稳定性

### 9.1 `Target` 装甲板匹配越界读

```cpp
// 原来硬编码 3，armor_num_ < 3 时越界
xyza_i_list.resize(3);
// 改为
xyza_i_list.resize(std::min(3, armor_num_));
```

平衡步兵（2 块装甲板）和单块调试（1 块）时会直接崩。

### 9.2 `diverged()` 发散误判

现象：自瞄启动几秒后云台停转，日志里 `[Tracker] Target diverged!` 反复出现。

链路：`diverged()` 判真 → `tracker` 强制 `state_ = "lost"` → 云台冻结。

改了三轮：

1. 下限从 `0.02` 放宽到 `0.005`，并给前 15 帧豁免。
2. 短边追踪时取 `max(合并半径, 长边半径)` 判定。
3. 锁定前 15 帧不判发散。

**验证状态：`规避`，没有根治。**

日志显示 `ekf_.x[8]`（半径 `r`）**恒为负**（`r=-0.058, l=0.000` / `r=-0.367, l=-4.653` / `r=-0.241, l=-4.782` …），而门限要求 `r > 0.005 && r < 0.5`——永远不可能成立。三轮修改调的阈值和豁免期在结构上都无法改变这个结果。

真正的根因：`tasks/auto_aim/target.cpp` 的 `Q` 矩阵**第 8/9/10 行（对应 `r` / `l` / `h`）全为 0**，半径状态的**过程噪声为零**，协方差只减不增，一旦被推偏就永久冻结，再也回不来。正确做法是给这三个状态加过程噪声（或者约束半径为正、失败时重置该状态），而不是继续调阈值。

### 9.3 启动崩溃

`imu_enabled: true` 但 IMU 没插时，`main.cpp` 的姿态分支对空指针解引用直接崩。改成 `imu_enabled: false` + 姿态走电机编码器后，启动稳定性解决。

### 9.4 部署

- 加 `autostart_sentry.sh` + watchdog 看门狗，异常退出自动拉起。
- `fuck.sh` 一键编译 + 运行。

## 10. 遗留问题（诚实清单）

| 问题 | 严重度 | 说明 |
| --- | --- | --- |
| `Q` 矩阵 `r/l/h` 过程噪声为 0 | 高 | `diverged()` 误判的根因，目前只是放宽阈值规避 |
| 姿态无 roll | 中 | 两轴编码器的物理限制，需融合 IMU |
| pitch 量化 1° | 中 | 电控协议限制 |
| 弹速协议未定稿 | 中 | 视觉对 ×1 / ×10 / ×100 都做兼容，存在误接受垃圾值风险；正确做法是电控只发一个约定好的量纲 |
| 单相机无全向感知 | 中 | 同济原版三相机做 `lost` 后全向搜索，单相机重捕获能力受限 |
| 无底盘里程计 | 低 | 底盘平移时世界系不跟车，原地/微动瞄准不受影响 |
| 缓存空静默返回单位四元数 | 低 | 应改为告警 |
| `aimer.cpp` 里 `if (bullet_speed < 14) bullet_speed = 11;` | 低 | 上游是 `= 23`，本机的电控实测弹速偏低才改成 11；这个兜底本身应该更明确地记录来源 |

## 11. 如果重做一遍

1. **先对齐协议再写代码**。CAN 那一轮返工（绝对角 → 增量角 → 符号 → 限幅）本质上都是协议没谈清，每一条都花了一次上机。
2. **卡方门限、单位量纲这类"抄来的魔法数"，落地时立刻验证维度**。它们失效时不报错，只表现为"效果不好"，最难查。
3. **调试可视化要在开始调参之前就做好**。第 4 条（EKF 门限）就是靠 1 Hz 的 NIS 失败率打印才定位到的，之前全靠猜。
4. **`diverged()` 那三轮应该早点去读 `Q` 矩阵**。现象是"阈值不对"，根因是"状态没有过程噪声"，改阈值是白费功夫。
